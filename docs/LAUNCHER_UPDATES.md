# Обновления Windows-лаунчера

Реализовано 19 октября 2026 года. Первая версия с обновлятором — **0.1.1**.
Пользователи 0.1.0 должны один раз установить 0.1.1 вручную. Сам по себе ZIP на сервере не добавляет обновлятор в старый EXE.

## Публикация

1. Для следующего выпуска увеличьте `[workspace.package].version` в `Cargo.toml`, например с `0.1.1` до `0.1.2`, и обновите заголовок `packaging/README.txt`.
2. Из корня репозитория выполните `./scripts/package-release.ps1`. Скрипт проверяет форматирование, сборку, Clippy и тесты, собирает release EXE со статическим CRT и формирует `dist/EquestrianDreamLauncher-<версия>-windows-x64.zip`.
3. В админке загрузите этот ZIP и укажите **точно тот же номер версии**, с которым собран EXE. Архив содержит только `EquestrianDreamLauncher.exe` и `README.txt` в корне. Публикуйте стабильные версии `MAJOR.MINOR.PATCH`; встроенный Windows version resource также проверяется клиентом.
4. Backend вычисляет размер и SHA-256. Повторно публиковать тот же номер нельзя; для исправлений нужен новый номер и новая сборка.

Клиент не вызывает `POST /api/upload-launcher`, не использует административные cookie или Telegram-токен для обновлений.

Адрес обновлений берётся из общей конфигурации backend: `LAUNCHER_SERVER_URL`, затем `launcher-config.json` рядом с EXE, затем встроенная копия корневого JSON. Скрипт упаковки добавляет JSON в папку дистрибутива, но ZIP автообновления по-прежнему содержит только EXE/README. Внешний конфиг сохраняется при обновлении; если его нет, используется конфиг, встроенный в новую сборку.

## API

`GET /api/launcher-update?platform=windows-x64` на backend из конфигурации лаунчера:

```json
{
  "version": "0.1.2",
  "url": "/download/launcher/0.1.2.zip",
  "sha256": "64 шестнадцатеричных символа",
  "size": 14000000
}
```

Относительный URL разрешается относительно backend origin. Абсолютный URL допустим только с тем же origin. Требуется HTTPS; HTTP разрешён исключительно для loopback-разработки и fixtures. Перенаправления запрещены. Опубликованный файл должен отдаваться напрямую, без redirect на другой домен/порт. `/api/launcher-update` должен быть публичным, как и `/download/launcher/...`.

`404` означает отсутствие доступного обновления. Ошибки сети, JSON или HTTP при фоновой проверке записываются в лог и не мешают играть. При проверке 19 октября production endpoint возвращал `404` с `API endpoint not found`: нужно убедиться, что маршрут нового backend развёрнут, а после первой публикации endpoint отвечает `200` с указанными полями.

## Работа клиента

- Проверка выполняется асинхронно один раз при открытии приложения, в том числе при ошибке первоначального client-config. Предлагается только строго более новая версия по SemVer precedence; равная версия, отличия только build metadata и downgrade игнорируются.
- Предложение ждёт возвращения на главный экран: игра, авторизация, настройки и диагностика не прерываются.
- Пользователь выбирает «Обновить и перезапустить» или «Позже». При скачивании доступна отмена. Во время передачи управления помощнику отмена отключается. Закрытие окна остаётся доступным.
- Метаинформация ограничена 64 КиБ, ZIP — 256 МиБ, распакованные файлы — 512 МиБ, README — 1 МиБ. Проверяются точный размер, SHA-256, состав ZIP, типы записей, CRC при распаковке и заголовок Windows x64 PE. Никакие произвольные файлы из ZIP не выполняются и не записываются рядом с EXE.
- Staging `.launcher-update-*` создаётся рядом с текущим EXE, а не в папке Minecraft. Если папка установки недоступна для записи, обновление не закрывает текущий лаунчер: пользователь видит ошибку и может продолжить играть. Повышение привилегий не запрашивается.
- Встроенная версия staged EXE сверяется с опубликованной через Windows version resource. При несовпадении установка не начинается.

## Замена и восстановление

Текущий EXE копируется в staging как `updater-helper.exe` и запускается с внутренним флагом `--launcher-apply-update <plan.json>` **до** обычной инициализации приложения и single-instance mutex. Никакие PowerShell/batch-команды или скачанные скрипты не используются.

Помощник проверяет план, расположение файлов и их хеши, открывает дескриптор ещё работающего родительского процесса, сигнализирует готовность и ждёт его полного завершения. После этого повторно проверяет staging, сохраняет прежние EXE/README в `previous/` и заменяет только эти два файла. Новый EXE стартует с прежним рабочим каталогом и получает `--launcher-update-health <staging>`; после инициализации приложения и входа в UI event loop он создаёт `healthy`.

Если замена файлов не удалась, новый процесс не стартовал, завершился или не подтвердил запуск за 75 секунд, помощник останавливает его и восстанавливает старые файлы. Прежний лаунчер запускается с `--launcher-update-rollback`, пропуская проверку обновлений в этом запуске, и показывается сообщение об ошибке. Если восстановлению мешает блокировка/диск, резервная копия остаётся в `previous/`, а сообщение содержит путь. Подтверждение означает успешную инициализацию лаунчера, а не доступность игрового backend или успешный запуск Minecraft.

После успешной установки или отката staging помечается `complete`. При следующем обычном запуске завершённые staging-каталоги удаляются; ещё работающий помощник не удаляется. Незавершённые/аварийные каталоги сохраняются для восстановления. Настройки, Telegram-сессия, логи и Minecraft-файлы не входят в архив и не заменяются.

Откат покрывает ошибки замены и запуска; абсолютная гарантия восстановления после отключения питания во время записи не заявляется.

## Проверки

`launcher_update` в launcher-core: localhost HTTP fixtures для версий, относительных URL, отсутствия выпуска, небезопасных метаданных, SHA-256/размера, отмены, состава ZIP и PE. `self_update` в desktop: замена/откат, отсутствие README, частичная ошибка, блокировка EXE, повреждение staging, встроенная версия и ожидание/health-check процесса. Существующий UI-тест проверяет предложение, прогресс, ошибки, кнопки и блокировку Play при разных масштабах.

Для экспорта только новых UI-снимков:

```powershell
$env:LAUNCHER_UI_PREVIEW_DIR = "$PWD/target/ui-preview"
$env:LAUNCHER_UI_PREVIEW_FILTER = "update-"
cargo test -p launcher-desktop memory_screen_syncs_validates_saves_and_renders
```
