# Telegram-авторизация — 15 октября 2026

Лаунчер открывается на главном экране; страница входа вызывается нажатием на аватар/аккаунт слева сверху или «Войти и играть». Компонент `auth-panel.slint` показывает выбор Telegram и Discord. Telegram использует описанный ниже API; Discord пока показывает сообщение о том, что вход ещё не подключён. Для Telegram предусмотрены отдельный код, ожидание, ошибки, открытие бота, копирование ссылки и повторная попытка. «Другой способ» отменяет текущий запрос, «К лаунчеру» также закрывает страницу. После входа аватар открывает профиль с выходом из аккаунта. Изменения этого экрана не меняют сценарий Telegram-бота.

Вход работает через существующий Express backend из `E:\mc_launcher\web_mc_launcher`. Отдельный Node.js worker находится в `web_mc_launcher/bot/`; инструкция запуска — `bot/README.md` этого репозитория. Worker работает на отдельном хосте, получает Telegram updates и передаёт их в защищённый API backend. Только backend записывает общий `data/users.json`.

При первом входе бот предлагает выбрать свободный Minecraft-ник. После явного подтверждения создаётся запись `tg_<Telegram user.id>` с полями `telegramId`, `nickname`, `registrationStatus: "pending"` и без пароля. Повторный вход находит эту запись по Telegram ID. Любой статус, кроме `banned`, разрешает вход. Существующий offline-ник и Telegram username не являются доказательством владения старой записью.

Лаунчер создаёт запрос через `POST /api/auth/telegram/challenges`, показывает код и ссылку, открывает бота или копирует ссылку. Каждые 2 секунды проверяет статус с отдельным `X-Poll-Secret`; запрос живёт 5 минут. Подтверждение обменивается на непрозрачную сессию один раз. Отмена и новая попытка используют счётчик поколений: старый ответ не меняет текущий аккаунт. Если отмена совпала с выдачей сессии, лаунчер пытается её отозвать.

Сессия действует 30 дней без refresh-механизма. В Windows она сохраняется атомарно в `state/telegram-session.dat` с Windows DPAPI текущего пользователя и привязкой к URL backend; `settings.json` не содержит токенов. При открытии проверяется `/api/auth/me`. Выход удаляет локальный файл и вызывает `/api/auth/logout`; при ошибке серверного отзыва показывается сообщение. Уже запущенная игра не завершается.

`auth/telegram.rs` содержит клиент API и общий `TelegramAuthGate`. Desktop задаёт gate в `VanillaLaunchConfig.telegram_auth`. Ядро проверяет сессию перед backend-конфигурацией/загрузками; Vanilla и NeoForge повторяют проверку непосредственно перед созданием игрового процесса. Ник процесса обязан совпадать с серверным. Telegram-токен не передаётся Minecraft. У других библиотечных клиентов gate необязателен; Desktop всегда его подключает.

На веб-сервере задаётся `TELEGRAM_BOT_SECRET` (случайная строка не короче 32 символов). На хосте бота: тот же `TELEGRAM_BOT_SECRET`, `telegrambotapi` с токеном BotFather и `AUTH_API_URL` с HTTPS URL веб-сервера. Имя бота определяется через `getMe`. В Desktop поле `server_url` файла `launcher-config.json` должно указывать на этот же backend (по умолчанию `https://launcher.nevermoreland.ru/`; также допустим `https://89.125.214.122`). Файл рядом с EXE переопределяет встроенную копию, `LAUNCHER_SERVER_URL` имеет высший приоритет. Полный URL `/api/client-config` нормализуется до origin для всех сервисов и хранения сессии. Секреты не входят в EXE и дистрибутив.

Доступность `/api/client-config` не подтверждает наличие Telegram API. При диагностике 15 октября создание, опрос и отмена запроса входа успешно проверены на прежнем адресе `87.58.220.248:3000`; текущий адрес задаёт JSON-конфиг. HTTP 404 при `POST /api/auth/telegram/challenges` означает отсутствие API по выбранному адресу: нужно проверить адрес или обновить backend. HTTP 503 означает, что бот ещё не подключён. Лаунчер различает эти ошибки и ошибку подключения.

Backend хранит хеши сессий, запросы и offset в отдельном `data/telegram-auth-state.json`. Это служебное состояние, аккаунты остаются в `users.json`. После перезапуска сохраняются сессии и защита от повторной обработки. При переносе сервера резервируются оба файла.

Проверки: `npm run test:telegram` и `npm test` в веб-репозитории; `cargo test --workspace`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo build --release` здесь. `LAUNCHER_UI_PREVIEW_DIR` сохраняет в существующем UI-тесте также экран `telegram-login` при 100/125/150%.

Код проверяется локальными HTTP fixtures без настоящих Telegram сообщений. Живая проверка требует владельца зарегистрированного бота, заполненных серверных `.env` и доступного HTTPS backend.

Это реализованная версия сценария: предложение про отдельный Rust-сервер с SQLite и refresh-токенами в старом `FEATURE_PLAN.md` не описывает текущую архитектуру.

## Исправление запуска — 19 октября 2026

Прежний встроенный HTTP origin с портом 3000 возвращает 308 на HTTPS с портом 443. При смене порта reqwest удаляет Authorization, поэтому /api/auth/me возвращал 401 даже после успешного exchange. Desktop теперь использует конечный HTTPS origin и нормализует прежний production override. DPAPI-сессия старого production origin мигрирует на HTTPS после серверной проверки; привязка к другим backend не ослаблена.

«Войти и играть» запоминает запуск и после подтверждения в боте сохраняет сессию, устанавливает её в общий gate и один раз вызывает Play. Возврат отменяет ожидание. AuthenticationRequired больше не оставляет кнопку заблокированной. Ошибки сети/сервиса показывают диагностику и позволяют повторить Play без принудительного повторного входа.
